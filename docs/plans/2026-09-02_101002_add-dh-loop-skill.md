# dh-loop 반복 오케스트레이터 스킬 신규 추가 계획

`skills/dh-loop/SKILL.md`를 새로 만들어 dh-dev의 계획→실행→검토→커밋을 **위임 방식**으로 감싼다.
초기 계획 1회만 승인받고, 독립 검증 에이전트가 완료조건 미충족을 판정하면 무인으로 재계획→실행→재검증을 반복한다.
같은 항목이 개선 없이 2회 연속 불합격하면 증거를 모아 사용자를 호출하고 멈춘다.

> 참고: 이 계획의 산출물은 실행 코드가 아니라 마크다운 스킬 문서다. "시그니처"는 "각 단계의 입력·출력·실패 처리 규정"으로, "테스트"는 "문서 구조 점검 + 워크플로 예행"으로 읽는다.

> 주의: 이 문서는 1-e 적대적 검토 HIGH 9건을 반영한 개정판이다. 발견별 처리는 맨 끝 부록에 있다.

## 1. Requirements Summary

### 1.1 목표 문장 (1-c 확정)

`skills/dh-loop/SKILL.md`를 새로 만들어 dh-dev의 계획→실행→검토→커밋 절차를 위임 방식으로 감싸는 반복 오케스트레이터 스킬을 추가한다. 초기 계획 1회만 사용자 승인을 받고 이후에는 무인으로 돌며, 독립 검증 에이전트가 개발 완료조건 미충족을 판정하면 계획 단계로 되돌아가 재계획→재실행→재검증을 횟수 제한 없이 반복하되, 같은 항목이 개선 없이 2회 연속 불합격하면 증거와 함께 사용자를 호출해 멈춘다.

### 1.2 개발 방향

**간단한 (simple)**. 앞으로도 계속 쓰지만 확장 계획은 없는 실용 스킬이다. 네 축 요구는 다음과 같이 해석한다.

| 축 | 이 작업에서의 구체 요구 |
| --- | --- |
| 설정 외부화·하드코딩 제거 | 정체 임계값·기록 폴더·검증 모델·브랜치 규칙 등을 문서 안 `## 루프 상수` 표 한 곳에 모으고, 본문은 상수 이름으로만 참조 |
| 재사용 인터페이스 | 루프를 7개 단계로 쪼개고 각 단계의 입력·출력·실패 처리를 표로 규정 |
| 경계·예외 입력 처리 | dh-dev 문서 없음, 회차 기록 파일 손상, 기록 파일 복수 발견, 검증 응답 형식 위반, 중단 후 재개, 범위 이탈 재계획, 보호 브랜치에서 시작을 각각 규정 |
| 테스트·문서 커버리지 | 문서 구조 점검 항목 + 예행 시나리오 + 축소 실동 예행 + `README.md` 갱신 |

### 1.3 사용자 확정 사항

| 쟁점 | 확정 |
| --- | --- |
| 포함 방식 | 위임형 래퍼. dh-loop은 반복 제어만, 절차 본문은 dh-dev를 읽어 수행. 본문 복제 금지 |
| 반복 상한 | 무제한 |
| 승인 게이트 | 초기 계획 1회만. 이후 무인 |
| 합격 판정 | 실행 에이전트와 분리된 독립 검증 에이전트. 자기 승인 금지 |
| 정체 처리 | 같은 항목 개선 없이 2회 연속 불합격 시 증거·이력 보고 후 정지 |

### 1.4 계획이 결정한 사항 (사용자에게 다시 묻지 않음)

무인 루프는 사용자를 부를 수 없으므로 아래 세 가지는 이 계획이 결정한다. 근거를 함께 적는다.

| 쟁점 | 결정 | 근거 |
| --- | --- | --- |
| 실패 회차 커밋이 쌓일 브랜치 | 루프 시작 시 `dh-loop/<slug>` 전용 브랜치를 만들어 그 위에서만 회차 커밋을 쌓는다. 병합은 사용자만 결정 | 이 저장소의 유일한 무인 반복 선례 `skills/autoresearch/SKILL.md` 3절이 `git checkout -b autoresearch/<tag>`로 전용 브랜치를 만든다. 같은 선례를 따르는 것이 가장 안전하고 학습 비용이 낮다 |
| 문서 분량 상한 | 200줄에서 **280줄**로 올린다. 파일은 `skills/dh-loop/SKILL.md` 한 개를 유지하고 `references/`를 만들지 않는다 | 3.2가 요구하는 12개 절과 표를 실측 추정하면 약 250줄이다(1.5 참조). 200줄은 물리적으로 불가능하다. 위임형 래퍼는 "한 문서를 처음부터 끝까지 읽는다"가 계약이므로 참조 폴더로 쪼개면 계약이 흐려진다 |
| 불합격 회차의 계획 이력 표기 | `docs\plan_history.md`의 Status는 표준 닫힌 목록의 `Superseded`만 쓰고, 회차 정보는 같은 항목의 Summary 텍스트 맨 앞에 `[dh-loop round N 검증 불합격]`을 붙여 구분한다 | `skills/plan-context/references/templates.md` 154~163행이 Status를 6개 값의 닫힌 목록으로 정의한다. dh-loop은 plan-context 규약을 손대지 않기로 했으므로 새 Status 값을 만들 수 없다 |

### 1.5 분량 실측 추정 (280줄 근거)

| 절 | 예상 줄 수 | 절 | 예상 줄 수 |
| --- | --- | --- | --- |
| frontmatter | 4 | 회차 기록 파일 | 42 |

합계 약 245줄이다. 표 사이 빈 줄과 여유를 더해 **280줄**을 상한으로 둔다. dh-dev 본체가 236줄이므로 같은 규모대다.

## 3. Implementation Steps (구현 지침)

### 3.0 데이터 구조와 알고리즘 개요

루프 상태는 **저장소 안 마크다운 파일 한 개**에 남긴다. 세션 메모리는 대화 압축으로 사라지므로 쓰지 않는다.

- 위치: `docs\dh-loop\YYYY-MM-DD_HHMMSS_<slug>.md` (이 파일을 **회차 기록 파일**이라 부른다)
- 발견 방법: `docs\dh-loop\` 폴더를 훑어 `**Status**: Running` 또는 `Paused`인 파일을 찾는다. 별도 색인 파일은 만들지 않는다.
- `docs\plan_history.md`는 회차마다 dh-dev가 이미 계획 항목을 남기므로 그대로 두고, 회차 기록 파일에서 각 회차의 계획 문서 경로를 가리킨다.

루프 알고리즘 (의사코드):

```
load: dh-dev 문서 읽기 → 실패면 즉시 중단(3.5 참조)
기록 파일 사전 점검: LEDGER_DIR에 Running/Paused 파일이 있으면 3.2.9로 분기
round = 1
dh-dev Step 1 전체 수행 (1-a ~ 1-e)  ← 개발 방향 질문·재진술 게이트·적대적 미리보기 포함
dh-dev Step 2 수행 (사용자 승인)      ← 유일한 승인 지점

브랜치 준비:
    현재 브랜치가 PROTECTED_BRANCHES에 있거나 이름이 LOOP_BRANCH_PREFIX로 시작하지 않으면
        git checkout -b <LOOP_BRANCH_PREFIX><slug>   (이미 있으면 그 브랜치로 전환)
    전환 실패 → 정지하고 사용자 호출
회차 기록 파일 생성:
    Status = Running
    Goal = 1-c 확정 문장 그대로
    Approved file scope = 1회차 승인 계획의 "변경 대상 파일" 표에 적힌 경로 목록 그대로
    Working branch = 전환된 브랜치 이름
    1회차 맥락 = 1-a 분석 산출물 경로와 1-b 맥락 요약 본문을 그대로 보존

loop:
    각 단계 시작 전 기록 파일 Status를 다시 읽는다. Running이 아니면 진행하지 않고 정지
    기록 파일 Current phase = execute
    dh-dev Step 3 수행 (실행 에이전트)
    기록 파일 Current phase = verify
    독립 검증 에이전트 호출 → 항목별 PASS/FAIL 표 수신
    증거 없는 PASS는 FAIL로 강등
    기록 파일 Current phase = commit
    dh-dev Step 4 수행 (revision-tracker, 커밋 자동 진행)
    회차 결과를 기록 파일에 추가

    if 모든 항목 PASS:
        기록 파일 Status = Completed, plan_history Status = Completed
        사용자에게 완료 보고 (병합 여부는 사용자가 결정) → 종료
    정체 판정 실행
    if 정체:
        기록 파일 Status = Stopped (stagnation)
        증거·이력 보고 → 사용자 선택 대기 (처리 방법은 3.2.7 선택 표)
    round += 1
    기록 파일 Current phase = plan
    dh-dev Step 1-d, 1-e 재수행 (실패 항목 한정 재계획, 추가 입력은 3.3 참조)
    목표 문장 변경 여부 판정 (오케스트레이터 문자열 비교, 3.2.6-b)
    dh-dev Step 2는 자동 승인 (재정의 표 OV-1, 조건 네 가지 모두 충족 시)
```

### 3.1 단계 계약 (입력·출력·실패 처리)

문서에 아래 표를 그대로 싣는다. 이것이 "간단한" 방향의 재사용 인터페이스 요구를 충족한다. `Load`를 뺀 모든 단계의 입력 첫 칸은 **기록 파일 Status 확인(Running이어야 진행)**이다.

| 단계 | 입력 | 출력 | 실패 처리 |
| --- | --- | --- | --- |
| `Load` | `DHDEV_PATH` | dh-dev 절차 본문(문맥에 적재) | 읽기 실패 → 3.5 탐색 순서 → 전부 실패 시 즉시 중단 |
| `Round-Plan` | 기록 파일 Status 확인, 목표 문장, 1회차 맥락(dh-dev 1-a 분석 산출물·1-b 맥락 요약), 직전 회차 실패 항목·증거·시도 이력, 승인 파일 범위 | 계획 문서 경로, 목표 문장 변경 여부 판정, 대상 파일 목록 | 계획이 승인 파일 범위를 벗어남 → 사용자 호출 후 정지 |
| `Round-Execute` | 기록 파일 Status 확인, 계획 문서 경로 | 변경 파일 목록, 실행자 주장 체크리스트 | 실행 오류 → 실패 증거로 기록하고 다음 회차로 (재정의 표 OV-5) |
| `Round-Verify` | 기록 파일 Status 확인, 계획 문서 경로, 완료조건 목록, 적대적 테스트 절, 변경 파일 목록, 실행자 주장, 직전 회차 실패 이력 | 항목별 판정 표 | 형식 위반 → `VERIFIER_RETRY`회 재호출 → 그래도 위반이면 회차 전체 불합격 |
| `Round-Commit` | 기록 파일 Status 확인, 변경 파일 목록, 회차 번호, 작업 브랜치 이름 | 커밋 해시 | 커밋 실패 → 회차 기록에 남기고 다음 회차 진행, 정지하지 않음 |
| `Stagnation-Check` | 기록 파일 Status 확인, 이번 회차 실패 항목, 직전 회차 실패 항목 | 정체 여부와 대상 항목 | 직전 회차 기록이 없으면 정체 아님으로 판정 |
| `Stop-Report` | 회차 기록 파일 전체 | 사용자 보고문과 세 선택지 | 해당 없음 (마지막 단계) |

#### 3.2.1 frontmatter

```yaml

description: "Iterative wrapper around the dh-dev workflow. #### 3.2.2 위임 계약 절
```

다음 다섯 규칙을 문서에 넣는다.

1. 루프 시작 시 `DHDEV_PATH` 문서를 **처음부터 끝까지 한 번 읽는다**. 요약본이나 기억에 의존하지 않는다.
2. 각 회차의 계획·실행·검토·커밋은 dh-dev가 정의한 순서(Step 1 → Step 2 → Step 3 → Step 4)를 **그대로** 따른다. dh-loop은 어느 단계를 언제 부를지만 정한다.
3. dh-loop 문서는 dh-dev의 규칙을 **이름과 절 번호로만** 가리킨다. 규칙 내용을 옮겨 적지 않는다. 규칙을 언급하는 줄에는 반드시 `dh-dev`라는 낱말이 같은 줄에 있어야 한다.
4. dh-dev 문서를 수정하지 않는다. dh-loop이 필요로 하는 차이는 전부 `## 루프 재정의` 표로 처리한다.
5. dh-dev가 개정되면 dh-loop은 다음 실행에서 자동으로 새 절차를 따른다. 재정의 표의 대상 규칙 이름이 dh-dev에서 사라진 경우, 해당 행을 적용하지 않고 사용자에게 한 줄로 알린다.

#### 3.2.3 루프 상수 절

아래 표를 그대로 싣고, 본문 다른 곳에서는 값을 다시 쓰지 않고 상수 이름만 쓴다. 상수는 **11개**다.

| 상수 | 값 | 뜻 |
| --- | --- | --- |
| `DHDEV_PATH` | `skills\dh-dev\SKILL.md` | 절차 원본 문서 |
| `LEDGER_DIR` | `docs\dh-loop\` | 회차 기록 파일 폴더 |
| `MAX_ROUNDS` | `0` | 회차 상한. `0`이면 상한 없음 |
| `STAGNATION_LIMIT` | `2` | 같은 항목 연속 불합격 허용 횟수 |
| `CUMULATIVE_FAIL_LIMIT` | `4` | 같은 항목 누적 불합격 허용 횟수 (보조 안전장치) |
| `VERIFIER_MODEL` | `opus` | 검증 에이전트 모델 |
| `VERIFIER_EFFORT` | Large 회차 `max`, 그 밖에는 `high` | 검증 에이전트 추론 강도 |
| `VERIFIER_RETRY` | `1` | 출력 형식 위반 시 재호출 횟수 |
| `SCOPE_GUARD` | `on` | 승인 파일 범위 이탈 시 정지할지 여부 |
| `LOOP_BRANCH_PREFIX` | `dh-loop/` | 루프 전용 브랜치 이름 앞머리 |
| `PROTECTED_BRANCHES` | `main`, `master` | 회차 커밋을 쌓으면 안 되는 브랜치 |

**Large 회차의 뜻** — 그 회차의 dh-dev Step 3 티어 판정 결과가 `Large`로 나온 회차를 말한다. 티어 판정은 dh-dev Agent & Model Policy가 정한 대로 오케스트레이터가 한다. dh-loop은 별도 기준을 만들지 않는다.

**비기본값일 때의 동작** — 상수를 사용자가 바꿔 둔 경우 아래를 따른다.

| 상수 | 비기본값일 때 |
| --- | --- |
| `MAX_ROUNDS` | 값이 `1` 이상이면 그 회차를 끝낸 뒤 정지한다. 정체와 같은 형식으로 보고하되 사유를 `round-limit`으로 적고, 3.2.7 선택 표를 그대로 제시한다 |
| `SCOPE_GUARD` | `off`면 범위 이탈을 정지 사유로 삼지 않고 회차 기록에 `scope-exceeded`로 남긴 뒤 진행한다. 이때 OV-1 자동 승인 조건 (나)는 충족한 것으로 본다 |

#### 3.2.4 루프 재정의 절

먼저 **유효 범위** 문단을 둔다. 아래 두 문장은 리터럴로 그대로 넣는다(완료조건 DOD-08이 이 두 문장을 찾는다).

> 이 표의 행은 `LEDGER_DIR` 안에 `**Status**: Running`인 회차 기록 파일이 있는 동안에만 효력이 있다. 루프가 끝나 Status가 `Completed`·`Stopped`로 바뀌는 순간 dh-dev 원문이 그대로 되살아난다. 재정의는 dh-dev 파일을 고치는 방식이 아니라 dh-loop 실행 중에만 적용되는 상위 규칙이다. 표에 없는 모든 것은 dh-dev를 그대로 따른다. 각 단계는 시작 전에 이 파일의 Status를 다시 읽어 Running임을 확인한다.

| 번호 | 대상 (dh-dev/revision-tracker 규칙) | 재정의 내용 | 안전장치 |
| --- | --- | --- | --- |
| OV-1 | dh-dev Step 2 하드 게이트 | 1회차는 원문 그대로 사용자 승인. 2회차 이후 재계획은 자동 승인하고 회차 기록에 `Auto-approved (round N)`으로 남긴다 | 자동 승인은 (가) 목표 문장이 그대로이고 (나) 대상 파일이 승인 파일 범위 안이며 (다) 직전 회차 실패 항목만 다루고 (라) 그 회차 dh-dev 1-e 구조 점검과 단일 재수정 뒤에도 **미해결 HIGH 발견이 없을** 때만 가능. 하나라도 어기면 사용자 호출 후 정지 |
| OV-2 | revision-tracker 6절 Git Commit의 3지선다 | 무인 회차에서는 `Commit`을 자동 선택해 그대로 실행한다 | 커밋 대상 브랜치는 반드시 `LOOP_BRANCH_PREFIX`로 시작해야 한다. 커밋 메시지는 `/commit` 형식을 지키고, Claude·Anthropic 관련 귀속 표기를 넣지 않는다. 제목 끝에 `(dh-loop round N)`을 붙인다 |
| OV-3 | dh-dev Step 4 2항 (`Completed` 갱신) | 검증 에이전트가 전 항목 합격을 낸 회차에서만 `Completed`로 바꾼다. 불합격 회차는 Status를 `Superseded`로 두고, Summary 텍스트 맨 앞에 `[dh-loop round N 검증 불합격]`을 붙인다 | Status 값은 plan-context가 정한 표준 6개 값만 쓴다. 새 Status 값을 만들지 않는다. 실행자 주장만으로는 절대 `Completed`로 바꾸지 않는다 |
| OV-4 | dh-dev 1-b 개발 방향 질문, 1-c 재진술 게이트 | 1회차에만 수행하고 2회차 이후는 1회차 결과를 재사용한다 | 매 재계획 뒤 오케스트레이터가 계획 문서의 목표 문장과 기록 파일 `Goal`을 문자열로 견준다. 다르면 루프를 멈추고 사용자를 부른다 |
| OV-5 | dh-dev Step 3 7항 (오류 시 사용자 확인) | 오류를 실패 증거로 기록하고 다음 회차 재계획으로 넘긴다 | 같은 오류가 정체 판정에 걸리면 사용자 호출 |
| OV-6 | dh-dev 예외 표 "완료조건 달성 실패 시 사용자 질문" | 해당 항목을 불합격으로 처리하고 재계획한다 | 정체 판정 적용 |

이어서 **재정의하지 않는 것** 목록을 둔다. 1-e 적대적 계획 미리보기, 필수 계획 섹션 8개, 실행 후 증거 대조, revision-tracker의 수정내역 기록과 품질 점검, 모델·추론 강도 티어링, plan-context의 Status 값 목록은 모든 회차에서 원문대로 적용한다.

#### 3.2.5 회차 기록 파일 절

파일 형식을 예시로 규정한다. 아래 뼈대를 문서에 그대로 싣는다.

```markdown
# dh-loop run: 2026-09-02_101500_add-dh-loop

**Goal**: <1-c 확정 문장 한 줄>
**Status**: Running
**Started**: 2026-09-02 10:15:00
**Last updated**: 2026-09-02 11:40:12
**Current round**: 2
**Current phase**: verify
**Approved file scope**: skills/dh-loop/SKILL.md, README.md
**Working branch**: dh-loop/add-dh-loop

## 1회차 맥락 (재계획용 보존)

- dh-dev 1-a 분석 산출물: <경로 또는 요지 5줄 이내>
- dh-dev 1-b 맥락 요약: <본문 그대로 보존>
- dh-dev 1-b 개발 방향: 간단한 (simple)

## 회차 요약

| 회차 | 계획 문서 | 변경 파일 수 | 판정 | 불합격 항목 키 | 커밋 |
| --- | --- | --- | --- | --- | --- |
| 1 | docs\plans\2026-09-02_101800_....md | 2 | FAIL | ledger-format, verifier-contract | a1b2c3d |

## 회차 1 상세

### 불합격 항목
| 항목 번호 | 안정 키 | 완료조건 원문 | 실패 요지 | failure_signature |
| --- | --- | --- | --- | --- |
| DOD-06 | ledger-format | 회차 기록 형식 예시가 문서에 있다 | 예시 표에 커밋 열 없음 | missing-column:commit |

### 시도했다가 실패한 접근
- 회차 기록을 plan_history.md에 합쳐 쓰기 — 인덱스 형식이 깨져 되돌림

### 정체 계수기
| 안정 키 | 연속 불합격 | 누적 불합격 | 직전 failure_signature |
| --- | --- | --- | --- |
| ledger-format | 1 | 1 | missing-column:commit |
```

규칙:

1. 각 회차가 끝날 때마다 **바로** 갱신한다. 회차 도중 단계가 바뀌면 `Current phase`도 그때그때 갱신한다.
2. 완료조건 항목마다 회차 안 번호(`DOD-<n>`)와 **안정 키**를 함께 적는다. 안정 키는 `<검증 대상>-<검증 성질>` 꼴의 소문자 하이픈 낱말이다.
3. `Approved file scope`는 1회차에 사용자가 승인한 계획 문서의 "변경 대상 파일" 표에 적힌 경로 목록을 **그대로** 옮겨 적는다. 승인 시점에 따로 되묻지 않는다. 이후 회차에서 이 값을 늘리려면 사용자 확인이 필요하다.
4. `## 1회차 맥락` 절은 1회차에 한 번 채우고 이후 회차에서 지우지 않는다. 대화가 압축되어도 이 절만 읽으면 dh-dev 1-d 입력 계약을 다시 갖출 수 있어야 한다.
5. 기록 파일이 없거나 형식이 깨져 읽히지 않으면 새 기록 파일을 만들고 회차 번호를 1로 되돌린 뒤, 그 사실을 사용자에게 한 줄로 알린다. 깨진 파일은 지우지 않고 `**Status**: Corrupted`로 표시한다.

#### 3.2.6 독립 검증 에이전트 절

**(a) 검증 계약**

| 항목 | 규정 |
| --- | --- |
| 모델·강도 | `VERIFIER_MODEL` / `VERIFIER_EFFORT` |
| 스폰 방식 | dh-dev Agent & Model Policy의 스폰 방식을 그대로 따르되, 에이전트에 파일 읽기 도구와 명령 실행 도구를 반드시 포함한다. 파일 쓰기 도구는 주지 않는다 |
| 격리 | 실행 에이전트와 별개의 새 에이전트로 띄운다. 실행 에이전트의 대화 맥락을 물려받는 방식(fork)은 금지한다. 실행과 검증을 같은 회차에 동시에 돌리지 않고 순서대로 돌린다 |
| 입력 | 계획 문서 경로, 완료조건 목록(번호+안정 키), 적대적 테스트 절, 변경 파일 목록, 실행자 주장 체크리스트(반드시 "주장"이라고 표시), 직전 회차 실패 이력 |
| 금지 | 실행자 주장을 근거로 합격을 매기는 것. 파일을 직접 읽거나 명령을 직접 돌려 확인한 것만 근거가 된다 |
| 출력 형식 | 첫 줄 `VERDICT: PASS` 또는 `VERDICT: FAIL`, 이어서 아래 표 |

```
| 항목 번호 | 안정 키 | 판정 | 증거 | failure_signature |
```

- 증거 칸은 실행한 명령과 출력 일부, 또는 `파일경로:줄번호` 인용이어야 한다.
- 합격 항목도 증거를 반드시 적는다.
- `failure_signature`는 합격 항목에서 빈칸, 불합격 항목에서 `<실패 유형>:<관측값>` 한 줄이다.

증거 누락 처리:

1. 오케스트레이터가 표의 각 합격 행을 확인해, 증거 칸이 비었거나 명령·파일 인용이 없으면 그 항목을 **불합격으로 강등**하고 `failure_signature`를 `no-evidence`로 적는다.
2. 응답에 표 자체가 없거나 첫 줄 판정이 없으면 `VERIFIER_RETRY`회까지 형식을 다시 지정해 재호출한다.
3. 재호출 후에도 형식을 못 갖추면 그 회차는 전체 불합격으로 처리하고, 모든 항목의 `failure_signature`를 `verifier-format-error`로 기록한다.

**(b) 목표 문장 변경 판정** — 검증과 별개로, 재계획이 끝날 때마다 오케스트레이터가 직접 한다. 에이전트에 맡기지 않는다.

1. 새 계획 문서의 목표 문장과 기록 파일 `Goal` 값을 꺼낸다.
2. 앞뒤 공백 제거와 연속 공백 축소만 하고 두 문자열을 견준다.
3. 다르면 자동 승인을 하지 않고 정지해 사용자를 부른다. 같으면 OV-1 조건 (가)를 충족한 것으로 본다.

#### 3.2.7 정체 판정 절

두 물음을 순서대로 판단한다.

**같은 항목인가** — 안정 키가 같으면 같은 항목이다. 완료조건 문구가 바뀌어도, 회차 안 번호가 바뀌어도 안정 키가 같으면 같은 항목으로 본다. 재계획할 때 계획 에이전트에게 직전 회차의 안정 키 목록을 넘기고, **같은 것을 검증하는 항목에는 반드시 같은 안정 키를 다시 쓰라**고 지시한다. 새 안정 키는 검증 대상이 실제로 새로 생겼을 때만 만든다. 미충족 항목을 재계획에서 지우는 것은 금지한다. 지워야 한다면 루프를 멈추고 사용자를 부른다.

**개선이 없었는가** — 아래 둘이 모두 참이면 그 항목의 연속 불합격 계수를 1 올린다.

1. 같은 안정 키가 이번 회차와 직전 회차 모두 불합격이다.
2. 두 회차의 `failure_signature`가 정규화 후 같다. 정규화는 앞뒤 공백 제거, 연속 공백 하나로 축소, 영문 소문자화, 숫자를 `#`로 치환하는 네 가지만 한다.

`failure_signature`가 다르면 진전이 있었다고 보고 그 항목의 연속 계수를 0으로 되돌린다. 다만 누적 불합격은 계속 올린다.

정지 조건:

- 어느 항목의 연속 불합격이 `STAGNATION_LIMIT`에 이르면 정지한다.
- 보조 안전장치로, 실패 요지가 계속 바뀌더라도 어느 항목의 누적 불합격이 `CUMULATIVE_FAIL_LIMIT`에 이르면 정지한다. 이때 보고문에 "실패 양상이 계속 바뀌었으나 누적 한도 도달"이라고 밝힌다.
- 직전 회차 기록이 없는 1회차에서는 정체 판정을 하지 않는다.

정지 보고문에 담을 것: 목표 문장, 회차 수, 정체 항목의 안정 키와 완료조건 원문, 회차별 `failure_signature` 나열, 시도했다 실패한 접근 목록, 회차별 커밋 해시, 작업 브랜치 이름, 회차 기록 파일 경로.

**사용자 선택별 처리** — 보고 뒤 아래 세 선택지를 제시하고, 고른 대로만 움직인다.

| 선택 | 처리 |
| --- | --- |
| 계속 | 정체 항목의 **연속 계수만 0으로 되돌리고 누적 계수는 그대로 둔다**. 기록 파일 Status를 `Running`으로 되돌리고 다음 회차 재계획부터 재개한다. 누적 계수가 이미 `CUMULATIVE_FAIL_LIMIT`에 있으면 사용자에게 `CUMULATIVE_FAIL_LIMIT`을 올릴지 한 번 더 묻고, 올리지 않으면 중단으로 처리한다 |
| 계획 수정 | 사용자가 준 수정 사항을 3.3 재계획 입력에 항목으로 더한다. 정체 항목의 연속·누적 계수를 **둘 다 0으로** 되돌린다. Status를 `Running`으로 되돌리고 재계획부터 재개한다 |
| 중단 | 기록 파일 Status를 `Stopped`로 확정하고 루프를 끝낸다. 작업 브랜치와 회차 커밋은 그대로 남긴다. plan_history의 해당 계획은 `Superseded`로 두고 Summary 앞에 `[dh-loop round N 검증 불합격]`을 붙인다 |

계수를 되돌리지 않고 재개하면 다음 회차에 곧바로 다시 정지하므로, "계속"에서 연속 계수 초기화는 필수다.

#### 3.2.8 커밋·브랜치 정책 절

**브랜치**

- 루프는 1회차 승인 직후, 첫 실행 전에 `<LOOP_BRANCH_PREFIX><slug>` 브랜치를 만들어 그리로 옮긴다. 같은 이름이 이미 있으면 새로 만들지 않고 그 브랜치로 옮긴다.
- 현재 브랜치가 `PROTECTED_BRANCHES` 안에 있으면 브랜치 전환 없이는 어떤 회차 커밋도 하지 않는다.
- 전환에 실패하면 정지하고 사용자를 부른다. 미커밋 변경은 전환 시 함께 따라온다.
- 브랜치 이름을 회차 기록 파일 `Working branch`에 남긴다. 매 커밋 전에 현재 브랜치가 그 값과 같은지 확인한다.
- 루프가 끝나도 dh-loop은 병합하지 않는다. 병합·되돌림은 사용자만 결정한다.

**커밋**

- **회차마다 커밋한다.** 합격 회차든 불합격 회차든 마찬가지다.
- 실패한 회차의 변경은 **되돌리지 않는다**. 다음 회차가 그 위에서 고친다. 되돌림은 사용자만 결정한다.
- 회차별 커밋이 있으므로 어느 회차로든 사용자가 직접 돌아갈 수 있다. 정지 보고문에 회차별 커밋 해시를 넣는 이유가 이것이다.
- 커밋 제목 끝에 `(dh-loop round N)`을 붙여 회차를 구분한다.

#### 3.2.9 중단과 재개 절

시작할 때 `LEDGER_DIR`를 훑어 `Running` 또는 `Paused`인 기록 파일을 찾는다.

| 찾은 개수 | 처리 |
| --- | --- |
| 0개 | 새 루프를 시작한다 |
| 1개 | Status를 `Paused`로 바꾸고 사용자에게 이어서 할지, 새로 시작할지, 끝낼지 묻는다 |
| 2개 이상 | 모두 `Paused`로 바꾸고 목록(파일 경로, 목표 문장, 회차, 작업 브랜치)을 보여준 뒤 어느 것을 이어갈지 사용자에게 고르게 한다. 고르지 않은 것은 `Paused`로 남긴다. 루프는 한 번에 하나만 돈다 |

이 물음은 루프가 돌기 전이므로 무인 규칙을 어기지 않는다.

이어서 하기로 하면 `Current phase`에 따라 재개한다. 재개 전에 `Working branch`로 옮긴다.

| 기록된 단계 | 재개 지점 |
| --- | --- |
| `plan` | 그 회차의 재계획부터 다시 |
| `execute` | 그 회차의 실행부터 다시 (부분 변경이 남아 있어도 실행 에이전트가 이어서 고침) |
| `verify` | 그 회차의 검증부터 다시 |
| `commit` | 그 회차의 커밋부터 다시. 이미 커밋되어 있으면 건너뛰고 다음 회차로 |

어느 경우든 회차 중간부터가 아니라 **그 단계의 처음부터** 다시 한다. 같은 단계를 두 번 돌려도 결과가 같도록 각 단계는 이전 산출물을 덮어쓴다.

#### 3.2.10 예외 절

| 상황 | 처리 |
| --- | --- |
| `DHDEV_PATH` 문서를 읽을 수 없음 | 3.5의 탐색 순서를 따르고, 전부 실패하면 즉시 중단 |
| 회차 기록 파일이 깨짐 | 새 파일을 만들고 회차 1부터. 깨진 파일은 `Corrupted`로 표시하고 남김 |
| `Running`·`Paused` 기록 파일이 2개 이상 | 목록을 보여주고 사용자가 하나를 고름. 나머지는 `Paused`로 남김 |
| 검증 응답 형식 위반 | `VERIFIER_RETRY`회 재호출 후 회차 전체 불합격 |
| 재계획이 승인 파일 범위를 벗어남 | `SCOPE_GUARD`가 `on`이면 정지하고 사용자에게 범위 확장을 확인. `off`면 기록만 남기고 진행 |
| 재계획이 목표 문장을 바꾸려 함 | 정지하고 사용자 호출 |
| 재계획에 미해결 HIGH 발견이 남음 | 자동 승인하지 않고 정지해 사용자에게 발견을 보임 |
| 보호 브랜치에서 루프를 시작함 | 전용 브랜치를 만들어 옮긴 뒤 진행. 전환 실패 시 정지 |
| `MAX_ROUNDS`에 도달 | 그 회차를 끝내고 사유 `round-limit`으로 정지, 3.2.7 선택 표 제시 |
| 커밋 실패 | 회차 기록에 남기고 다음 회차 진행. 정지하지 않음 |
| `git` 저장소가 아님 | 브랜치·커밋 단계를 건너뛰고 회차 기록에 `no-git`으로 남긴 뒤 계속 |
| 재정의 표의 대상 규칙이 dh-dev에서 사라짐 | 그 행을 적용하지 않고 사용자에게 한 줄로 알림 |
| 사용자가 중간에 끊음 | 다음 실행 때 3.2.9로 재개 |

### 3.3 재계획 입력

2회차 이후 dh-dev 1-d 계획 에이전트에 아래를 **추가로** 넘긴다. 문서에 이 목록을 그대로 싣는다. 1번과 2번은 dh-dev 1-d가 요구하는 입력 계약을 무인 회차에서도 채우기 위한 것이다.

1. 회차 기록 파일 `## 1회차 맥락` 절의 dh-dev 1-a 분석 산출물 (경로 또는 요지)
2. 회차 기록 파일 `## 1회차 맥락` 절의 dh-dev 1-b 맥락 요약과 개발 방향
3. 목표 문장 (기록 파일 `Goal` 값 그대로)
4. 직전 회차의 불합격 항목 표 (번호, 안정 키, 완료조건 원문, 실패 요지, `failure_signature`)
5. 누적 "시도했다가 실패한 접근" 목록 전체
6. 직전 회차 계획 문서 경로
7. 합격 항목 목록과 "이미 충족 — 이번 회차에서는 되돌아가지 않았는지만 확인" 지시
8. 승인 파일 범위
9. 지시문: "직전 회차와 같은 접근을 되풀이하지 말 것. 되풀이가 불가피하면 이번에는 무엇이 다른지 한 줄로 적을 것."
10. 지시문: "직전 회차의 안정 키를 그대로 다시 쓸 것. 미충족 항목을 지우지 말 것."

### 3.4 금지 문자열 목록 (본문 복제 방지)

dh-loop 문서에 아래 문자열이 나타나면 절차 복제로 본다. 규칙 이름을 가리켜야 할 때는 같은 줄에 `dh-dev`를 함께 적는다.

| 금지 대상 | 허용 형태 |
| --- | --- |
| `### 1-a`, `### 1-b`, `### 1-c`, `### 1-d`, `### 1-e` 꼴의 제목 | 본문 안에서 `dh-dev 1-d`처럼 이름으로만 언급 |
| `Required Plan Sections`를 나열하는 목록 | `dh-dev 1-d의 필수 계획 섹션` 한 줄 언급 |
| `Classification checklist`, `Tier resolution rule`의 판정 내용 | `dh-dev의 모델·effort 티어링을 그대로 따른다` 한 줄 |
| 개발 방향 4축 표 | `dh-dev 1-b의 범용성 표를 따른다` 한 줄 |

### 3.5 dh-dev 문서 탐색 순서

1. `skills\dh-dev\SKILL.md` (현재 작업 폴더 기준)
2. 플러그인 설치 경로의 `skills\dh-dev\SKILL.md`
3. 사용자에게 경로를 한 번 묻는다

셋 다 실패하면 아래 문구로 중단한다. 절차를 짐작해서 대신 수행하는 것은 금지한다.

> dh-dev 절차 문서를 찾지 못해 dh-loop을 시작할 수 없습니다. dh-loop은 dh-dev의 절차를 읽어 수행하는 래퍼이므로, 절차 원본 없이는 어떤 회차도 시작하지 않습니다. `skills\dh-dev\SKILL.md` 경로를 알려주시면 이어서 진행합니다.

### 3.6 README 갱신

- 스킬 목록 표는 현재 **22행**(`README.md` 파일 9~30행)이다. `dh-dev` 행(파일 24행) 바로 다음에 한 행을 넣어 **23행**으로 만든다.
  `| [dh-loop](skills/dh-loop/) | dh-dev 반복 오케스트레이터 (무인 재계획→실행→독립 검증 루프) | - |`
- 디렉토리 구조 트리에서 `dh-dev/` 항목 다음에 아래를 넣는다. 들여쓰기와 화살표 정렬을 주변 줄에 맞춘다.

```
│   ├── dh-loop/
│   │   └── SKILL.md              ← dh-dev 반복 래퍼 (독립 검증·정체 감지)
```

- `docs/` 트리의 `plans/` 아래에 `dh-loop/  ← dh-loop 회차 기록` 한 줄을 넣는다.

## 4. Code Writing Guide (코드 작성 가이드)

### 4.1 문서 관례

| 항목 | 규칙 |
| --- | --- |
| 파일 위치 | `skills/dh-loop/SKILL.md` 한 개. `references/` 폴더는 만들지 않는다 (근거는 1.4) |
| 인코딩 | UTF-8, 바이트 순서 표식 없음. 줄 끝은 저장소 기존 파일과 동일 |
| frontmatter | `name`과 `description` 두 필드만. `allowed-tools`는 넣지 않는다 |
| `description` | 영문 한 줄 큰따옴표 문자열. 화살표 요약 → `Use when:` → `Triggers:` 순서. 한국어 트리거 낱말 섞어 쓰기 |
| YAML 안 경로 | 역슬래시를 두 번 쓴다 (`docs\\dh-loop\\`) |
| 본문 안 경로 | 역슬래시 한 번, 백틱으로 감싼다 (`docs\dh-loop\`) |
| 제목 | dh-dev와 같이 한국어 병기 (`## 루프 재정의 (Loop Overrides)`) |
| 절 개수 | 12개 고정. 새 절을 늘리지 않는다 |
| 표 중심 | 세 개 이상 나열은 반드시 표나 목록 |
| 강조 | 용어 첫 등장 굵게, 파일명·명령·식별자는 백틱 |
| 중요 표시 | `> 참고`, `> 주의` 인용 블록만 사용. 이모지 금지 |
| 금지 문자 | `§` |
| 금지 표현 | i.e., e.g., etc., N/A → "즉", "예를 들어", "등", "해당 없음" |
| 용어 정리 | 문서 맨 끝에 가나다순 표 |
| 분량 | **280줄 이하**. 250줄을 넘어서면 절차를 복제하고 있는지 3.4 금지 목록으로 먼저 확인할 것 |

### 4.2 따를 패턴

- dh-dev의 문체를 그대로 따른다. 짧은 선언문, 표, 규칙 번호.
- 첫머리에 파이프라인 그림과 `> **Effort:**` 블록쿼트를 둔다. dh-dev와 같은 형식이되 문구는 dh-loop 사정에 맞게 새로 쓴다.
- 브랜치 격리는 `skills/autoresearch/SKILL.md`의 전용 브랜치 방식을 따른다. 이름 앞머리만 다르다.
- 상수는 `## 루프 상수` 표 한 곳에만 값이 있고, 다른 곳은 이름만 쓴다.

### 4.3 피할 패턴

- dh-dev 절차 문장을 복사하기
- 값(숫자·경로)을 본문 여러 곳에 흩뿌리기
- plan-context가 정한 Status 목록에 없는 값 만들기
- "적절히", "필요하면", "잘" 같은 판단을 실행자에게 미루는 표현
- 새 색인 파일, 새 스크립트, 새 참조 폴더 만들기
- dh-dev·revision-tracker·plan-context 파일 수정

### 4.4 이름 규칙

| 대상 | 규칙 | 보기 |
| --- | --- | --- |
| 스킬 이름 | 폴더명과 같은 kebab-case | `dh-loop` |
| 상수 | 대문자 밑줄 | `STAGNATION_LIMIT` |
| 회차 기록 파일 | `YYYY-MM-DD_HHMMSS_<slug>.md` | `2026-09-02_101500_add-dh-loop.md` |
| 작업 브랜치 | `dh-loop/<slug>` | `dh-loop/add-dh-loop` |
| 완료조건 번호 | `DOD-<두 자리>` | `DOD-06` |
| 안정 키 | 소문자 하이픈, `<대상>-<성질>` | `ledger-format` |
| 실패 요지 | `<유형>:<관측값>` | `missing-column:commit` |

### 4.5 의존 제약

새 실행 파일·패키지·스크립트를 추가하지 않는다. dh-loop은 dh-dev, revision-tracker, plan-context, `/commit` 스킬과 파일 읽기·쓰기·git만 쓴다.

### 6.5 축소 실동 예행 (AT-52)

문구만 채워도 정적 점검을 통과할 수 있으므로, 루프가 실제로 도는지 한 번 확인한다. 축소 시나리오 **1개**만 돌린다. 개발 방향이 "간단한"이므로 이 이상 늘리지 않는다.

절차:

1. 임시 폴더 `docs\dh-loop\_dryrun\`에 3.2.5 형식의 가짜 회차 기록 파일을 하나 만든다. `Status: Running`, `Current round: 1`, 가짜 불합격 항목 1개(안정 키 `dry-item`, `failure_signature`는 `missing-line:foo`)를 넣는다.
2. `skills/dh-loop/SKILL.md`만 읽고, 사람 개입 없이 아래 다섯 가지를 순서대로 도출할 수 있는지 확인한다.
   - 2회차 재계획에 넘길 입력 10개를 실제로 나열할 수 있다
   - 2회차 자동 승인 가능 여부를 조건 (가)~(라)로 판정할 수 있다
   - 검증 에이전트에 넘길 입력과 요구 출력 형식을 그대로 적을 수 있다
   - 검증 응답이 "합격, 증거 칸 빈칸"으로 왔을 때 `no-evidence` 강등을 적용할 수 있다
   - 2회차도 `missing-line:foo`로 불합격이라 가정했을 때 정체 정지가 걸리고, 사용자가 "계속"을 고른 뒤 계수가 어떻게 바뀌는지 답할 수 있다
3. 다섯 가지 중 하나라도 답이 없거나 둘 이상이면 그 항목을 불합격으로 적고 문서를 고친 뒤 6.2부터 다시 한다.
4. 확인이 끝나면 `docs\dh-loop\_dryrun\`을 지운다. 저장소에 남기지 않는다.

이 예행은 실제 dh-dev 회차를 돌리지 않는다. 문서가 무인 판단을 실제로 내리게 하는지만 본다.

## 8. Verification Steps

1. `skills/dh-loop/SKILL.md`를 작성한다. 3.2의 절 순서 12개를 그대로 지킨다.
2. `README.md`를 3.6대로 고친다. 고치기 전에 스킬 목록 표 행 수가 22행인지 먼저 세고, 고친 뒤 23행인지 다시 센다.

5. 6.5의 축소 실동 예행(AT-52)을 돌리고 임시 폴더를 지운다.
6. 문서 검증 스크립트를 돌린다.

```powershell
$env:PYTHONUTF8='1'
$env:PYTHONIOENCODING='utf-8'
python C:\Users\donghun.lee\.codex\skills\.system\skill-creator\scripts\quick_validate.py .\skills\dh-loop
python C:\Users\donghun.lee\.codex\skills\.system\plugin-creator\scripts\validate_plugin.py .
```

두 스크립트가 없는 환경이면 그 사실을 증거에 적고 6.2 정적 점검으로 대신한다.

7. `git status --short`와 `git diff --stat`으로 변경 파일이 `skills/dh-loop/SKILL.md`와 `README.md` 둘뿐인지 확인한다. `skills/dh-dev/SKILL.md`가 변경 목록에 있으면 즉시 되돌린다.

10. 완료 보고에 실행한 명령, 그 출력의 요지, 완료조건 대조표를 함께 낸다.
